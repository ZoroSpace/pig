# VS16 emoji 宽度算 1 格 → 终端提前折行 → 流式渲染帧失同步（鬼影 + Working 边框插行）

日期：2026-09-22；状态：已收口；涉及：tui/utils.go、tui/grapheme_width_vs16_test.go
本质：对 2026-09-21 `2026-09-21-vs16-emoji-width-table-misalign.md` 的**结论纠正与回滚**。

## 现象

dogfooding（iTerm2 直跑，无 tmux）中 agent 流式回复渲染大面积错乱：

- 含 `⚠️` 的行反复留下**逐帧变长的前缀鬼影**（同一逻辑行的历史帧纵向堆叠）；
- 编辑器顶边框（内嵌 `─ ⠦ Working ─` spinner 行）出现在**正文中间**；
- 行尾字符（全角标点等）残留在错误位置。

所有鬼影行都含 `⚠️`（U+26A0 U+FE0F）；纯英文段落若引用了含 `⚠️` 的片段同样复现。

## 根因

`graphemeWidth` 对「EAW neutral/ambiguous 基字符 + VS16」的 RGI emoji（⏸️ ⚠️ ❤️ ☀️）返回 **1**
（前一批修复引入）。但真实终端渲染 **2** 格。

**实测（DSR 法）**：向终端写入序列后发 `ESC[6n` 光标位置查询，读回列号即真实占格。
同一探针跑两遍（tmux 3.7c pane 内 / iTerm2 直跑）：

| 序列 | pig（修复前） | tmux 3.7c | iTerm2 直跑 |
|---|---|---|---|
| `中` | 2 ✓ | 2 | 2 |
| `├`（ambiguous） | 1 ✓ | 1 | 1 |
| `⚠`（无 VS16） | 1 ✓ | 1 | 1 |
| **`⚠️`** | **1 ✗** | **2** | **2** |
| **`⏸️`** | **1 ✗** | **2** | **2** |
| `❤️` `☀️` | 1 ✗ | 2 | 2 |
| `#️⃣` | 2 ✓ | 2 | 1（反向偏差，见下） |
| `❌` `✅` `🇺🇸` | 2 ✓ | 2 | 2 |

**失同步链条**：pig 算 1、终端画 2 → 含该 emoji 的逻辑行实际渲染宽度比 pig 以为的多 1 格 →
该行恰在折行边界时终端提前折行（多占一行物理行）→ 渲染器按自身行模型做相对光标移动与
`\x1b[2K` 清行，全部偏 1 行 → 每个流式帧重绘都残留一行历史帧，误差逐帧累积 →
鬼影堆叠 + Working 边框画进正文。上一批观察到的「表格边框错位」当时被归因于「算 2 vs 终端渲染 1」，
方向判断反了：真实表格修复是同日的 `1516868`（regexp2 字节偏移切坏 UTF-8 + 分隔线缺 `─`），
宽度改 1 后表格"看起来对齐"是 emoji 溢出 1 格与 padding 少 1 格在边框位置上相互抵消的视觉假象。

## 修复

`tui/utils.go`：删除 `isNarrowEmojiPresentation` 特例，恢复所有 RGI emoji 恒 2 格
（pi string-width 行为）。

**宽度取值的不对称原则**（本次教训，后续宽度类问题先想清楚方向）：

- **多算**（pig=2，终端=1）：永不触发提前折行，帧同步不受影响；最坏是表格 cell 内 padding 差 1 列（`#️⃣` 在 iTerm 渲 1 即此类，可接受）。
- **少算**（pig=1，终端=2）：边界行提前折行 → 帧失同步 → 全屏级鬼影（本次事故）。

不确定时**往宽了算**。

## 回归测试

`tui/grapheme_width_vs16_test.go`：10 个 graphemeWidth 单簇用例全部按实测真值翻转
（⏸️/⚠️/❤️/☀️ → 2；裸 `⏸` → 1；❌/😀/keycap/RI/ZWJ → 2）+ 复合串 VisibleWidth 用例
（`决策，⏸️ 按需延后` 16 → 17）。

## 教训

上一批的"地面真相"来自 pig 内部算术自洽（VisibleWidth 全等探针 + 测试全绿），**从未向真实终端
求证过渲染宽度**。终端宽度类问题的唯一可信证据是向真实终端发查询（DSR / cell size 等）读回的
结果；pig 内部探针只能证明 pig 自洽，不能证明 pig 与终端一致。
