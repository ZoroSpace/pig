## 3. 风险与坑（下一批大概率撞的）

1. **PrepareCompaction 现有签名/语义**：pig `PrepareCompaction(pathEntries, settings)` 与 pi 同形，但内部 cut-point 规则要整个换成 `findProjectedCutPoint`——存量 compaction 测试（keepRecentTokens 边界、split-turn、token 计算断言）先跑红面再改期望；pi 侧本轮无 compaction 测试增量，期望变化全部由 10 个 context-edit 用例 + 存量测试承载。
2. **`prevCompactionIndex` 语义变化**：旧逻辑「path 里最后一个 compaction 的下标」→ 新逻辑「投影 entries 里第一个 `messages.length > 0` 的 compaction」（老 compaction 投影为空被跳过）；boundaryStart 直接 = prevCompactionIndex+1，不再有 firstKeptEntryIndex 查找失败回落。
3. **`extractFileOperations` 的第三参**从 pathEntries 改为 sourceEntries（投影条目的 raw entry 切片）——pig 侧确认该 helper 的签名与调用点一起改，别漏 turn-prefix 那次调用。
4. **EstimateTokens 的 system 新分支**：sections 逐 value 累加（`Object.values` 忽略 undefined → pig `if section != nil`）、toolsAdded 走 JSON 长度；pig 的 SystemMessage.Sections 是保序自定义 map 类型，长度语义用字符串值长度。
5. **retain-none 落线形态**：`AppendCompaction(nil)` 写出的 `firstKeptEntryId` 是 compaction 自身 id（S8-2 已测）；S8-3 的 compact() 何时传 nil 由 pi `prepareCompaction` 返回的 firstKeptEntryId 是否为 compaction 自身决定——注意 pi 没有「传 nil」的 compact 路径，nil 只出现在 appendCompaction 参数默认层，pig 保持同构。
6. 大文件纪律照旧：compaction.go 一次 edit 多处；测试先读齐签名再动笔。
