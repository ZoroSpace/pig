## 0. 交付摘要

用户拍板「MCP OAuth 整族」开工，落地为 pig 原生实现（`integrations/mcp/oauth*.go`）。中途因 token 预算中断过一次（交接稿记录了挂起项），本会话完成剩余工作并收口。

1. **协议引擎全量**：发现（PRM/ASM 多候选 + 2025-03-26 fallback + authServerMetadataUrl 信任路）、PKCE、DCR、换码/刷新、RFC 9207 iss 校验、scope 合并/step-up、跨进程刷新 flock、`ErrSignInRequired` sentinel。
2. **传输层接入**：go-sdk `auth.OAuthHandler`（TokenSource + Authorize）为唯一接入点；非交互路永不开浏览器，静默刷新失败 → needs-auth。
3. **凭证存储**：`<agentDir>/mcp-auth.json`，键 `name|<serverURL>`，原子写 + 0600 + 跨进程 flock（unix；windows no-op 声明）。
4. **config 面**：`oauth.*` + `auth.provider` + `clientRegistration:"cimd"` fail-closed 拒绝；校验与 pi validateOAuth 对齐。
5. **面板面**：needs-auth 行 + ctrl+s 内嵌 sign-in 视图（URL 可复制 + 粘贴输入与回调竞速）+ ctrl+o 登出；键位 `app.mcp.signIn`/`app.mcp.signOut`。
6. **核心桥接**：`createMCPManager` 接 `CredentialStore`/`ProviderToken`/`ResolveConfigValue`；sdk/services 用 `ModelRegistry.GetApiKeyForProvider` 闭包喂 provider token。
7. **本会话修复**（收口前）：
   - **死锁（唯一阻塞项）**：`oauthHandler` 的 challenge 回调原用 `st.mu`，而 `connectLocked` 持 `st.mu` 调 `client.Connect`（go-sdk 在连接内同步回调 Authorize/onChallenge）→ 自死锁、`TestManagerNeedsAuthThenSignIn` 挂起。修：新增 `serverState.challengeMu` 独立锁（pig-only，pi 单线程无此隐患），回调用它，SignIn 读写用它。
   - **测试 bug**：`oauth_flow_test.go` 用 `http.Header{"WWW-Authenticate": ...}` 字面量键——非 canonical，`Header.Values` 取不到（实测），改用 `Header.Add`。
8. **本会话补测**：config OAuth 校验 6 错误面单测 + 面板 needs-auth 行/ctrl+s+esc/ctrl+o 三测。

## 3. 已声明偏差

- `clientRegistration:"cimd"` fail-closed 拒绝（pi.dev 基建不存在；用 DCR 或 oauth.clientId）。
- legacy URL 键凭证迁移不做（pig 无存量、`~/.pig` 与 `~/.pi` 隔离）。
- pi 的 `OAuthClientProvider` 抽象层与 codeVerifier/oauthState 持久化不移植（流内内存态）。
- 官方 conformance suite CI 不做。
- pi 的 `pi mcp login` CLI 子命令不做（pig 无该 CLI 面）。
- windows 跨进程刷新锁 no-op。
- 发现路 issuer 校验依赖 go-sdk `oauthex.GetAuthServerMeta`（附带强制 PKCE——服务器不声明 PKCE 支持时 pig 拒绝，pi 只在列出不含 S256 时拒绝）。
- go-sdk `auth.AuthorizationCodeHandler` 不采用（改用 oauthex 原语 + 手写流编排）。
