# SYNC-AUTOMATION：基线同步流水线的自动化方案（提案，待拍板）

- **日期**：2026-10-05
- **状态**：提案——三阶段方案尚未架设，本文档先记录问题、分析与设计；任何阶段落地前由用户拍板
- **起因**：S14（pi v1.0.2→v1.0.3）收口后，用户提出能否把「pi 出新版 → pig 同步」这套周期性流程自动化掉

## 1. 问题（口语原话润色）

> 每次 pi 发布新版本，我都要重复走一遍同样的流程：先让 agent 对照 pi diff 列出改造方案并落盘成 md；然后分批施工，每批起一个独立的 agent 会话执行，做完一批就写 handoff、commit 并 push，再起新的 agent 做下一批，直到所有批次做完。这套固定的流程能够自动化吗？

背景事实：pi 在 main 上开发、按节奏打 `Release v1.0.x` tag（无 release 分支，tag 后紧跟 `[Unreleased]` cycle 开启 commit），所以「pi 出新版本」是一个可程序化检测的事件（`git ls-remote --tags`）；而 pig 侧的同步流程自 S 系以来已经高度仪式化，每一步都有既定产物和验收标准。

## 2. 可行性依据：S14 已是单会话全程跑通的实证

S14 一轮（fetch pi diff → 逐 commit 分拣 22 个 → 落盘开工稿 → 施工实移 5 项 → 验收门 → tmux 冒烟 → handoff 回填 → commit push）由**一个 agent 会话连续完成**，无中途换手。因此「单批次执行」环节已被证明可以端到端自动化；剩余问题只是：

1. 把周期触发包装成自动化（定时检测新 tag）；
2. 划清哪些环节保留人工卡点。

另外，「每批起一个 agent」的换手机制不需要发明新东西——handoff 文档本来就是为此设计的（新 session 只读 AGENTS.md + 最新 handoff 即可开工）；拆批判断沿用既有规则（源码+测试合计 ≤6000 pig 行单批，超出按区分批）。

## 3. 自动化边界分析

### 3.1 可全自动的环节（机械步骤）

| 环节 | 做法 |
|---|---|
| 触发 | 定时任务检查 pi 仓库新正式 tag（`git ls-remote --tags` 对比 pig 基线常量） |
| 方案 | `git fetch` + `git diff v旧..v新` 逐 commit 分拣：实移 / 零操作，对照 AGENTS.md 不做清单与 pig-only 偏差清单；落盘 `docs/handoffs/SYNC-S<n>-v<版本>.md` 开工稿 |
| 施工 | 照开工稿逐项执行（pi 源文件路径、pig 落点、要移植的测试均已在开工稿中列全） |
| 验收门 | build / vet / gofmt 干净 + 全量 `-race` 单次（仓库机制：同一命令只跑一次）+ tmux 冒烟（env -i 清凭证 + mock provider + jsonl 抽查零真实 API） |
| 收口 | handoff 回填终稿 + AGENTS.md 批次索引一行 + commit（push/tag 见 3.2）+ 预写「下一批候选」段 |

### 3.2 需保留人工卡点的环节（不该全自动）

1. **开工稿拍板**。AGENTS.md 明文：「批次范围的决策权在人，模型只执行定义良好的批次」。开工稿自动落盘后由用户过目（≈2k token）再放行施工，成本趋近于零，但保住了范围决策权。
2. **计划外裁量**。每批都可能出现开工稿没预见的判断点，S14 实例：
   - models_generated.go 整体重生成会引入超出 pi 基线的 models.dev 漂移 → 临时决策改走机械变换（已记录在案例外）；
   - OAuth 刷新取消语义在 pig `CredentialStore.Modify` 契约下无法 1:1 → 记录偏差后取等价语义。
   缓解手段：把可预判的裁量固化进 AGENTS.md 预批准政策（见 §4 阶段 3 的清单），减少每批的临时拍板；无法预判的停下问人。
3. **push 与 tag**。建议自动化到本地 commit 为止；push（以及 tag）视信任建立程度决定放行或保留确认。commit 不 push 时，所有产出一个 `git log` 即可复核，回滚零成本。

## 4. 分阶段落地设计

### 阶段 1：监控 + 预消化（零风险，先做）

定时任务（如每日一次）：

1. `git ls-remote --tags` 检查 pi 新正式 tag，与 pig `codingagent/config.go` 基线常量比对；
2. 发现新 tag → 在 pi 仓库 `git diff <旧>..<新>` 逐 commit 分拣，写开工稿落盘 `docs/handoffs/`；
3. 通知用户「开工稿已就绪，待拍板」。

产出全部是文档，不触碰 pig 源码；同时把每批最贵的「重翻 pi diff」也提前消化掉了（这正是仓库机制「每批收口必须预写下一批 handoff」规则的延伸）。

### 阶段 2：拍板后一键开工

用户过目开工稿后说「开工」，agent 按 S14 的完整流程跑完单批：施工 → 验收门 → 冒烟 → handoff 回填 → commit。若开工稿判断体量超 6000 行，自动按区拆批并逐批走「做一批 → 写 handoff → 新 agent 接力」，全程无需用户再介入中间批次。

### 阶段 3：全自动（信任建立后）

出 tag → 写稿 → 施工 → 验收 → commit push 全自动，tag 可选自动打。放权前先把以下裁量固化为 AGENTS.md 预批准政策（每条都是 S 系已经出现过至少一次的判断）：

- catalog golden（`ai/testdata/*.json`）上游漂移的处理（C2 先例 + S14 的 models_generated 变换案例外）；
- 触碰不做清单 / pig-only 偏差清单的 commit → 一律零操作并记录，不升级；
- 分拣不干净（无法归类）的 commit → 停下来问人；
- 测试或冒烟红 → 停下来问人，不自行放宽验收。

## 5. 与既有规则的关系

- 不改变「钉正式 tag、永不追 main」的同步策略；
- 不改变「批次范围决策权在人」（阶段 1/2 均有拍板卡点）；
- handoff 交接、验收门、go test 执行规范、tmux 冒烟规则全部原样沿用——自动化只是把「人提醒 agent 走流程」换成「流程驱动 agent」；
- 本文档是提案记录，落地任一阶段时在 AGENTS.md 追加对应条目。
